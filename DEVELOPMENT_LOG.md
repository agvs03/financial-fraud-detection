# Development Log — Financial Fraud Detection

A complete record of how this project was built, every decision made along the way, the problems encountered, and why each was solved the way it was. Written July 2026.

---

## 1. The goal

The brief was an end-to-end, GitHub-ready deep-learning project for credit-card fraud detection containing: preprocessing of the Kaggle ULB credit-card dataset (284,807 transactions, ~0.17% fraud — severely imbalanced) with SMOTE oversampling and decision-threshold optimization; a full EDA notebook with correlation heatmaps, distribution plots, and statistical hypothesis testing; a TensorFlow/Keras ANN targeting roughly 96.8% recall on the fraud class; a comparison against Random Forest, XGBoost, and Logistic Regression baselines; a full evaluation suite (precision-recall curves, F1, confusion matrix, AUC-ROC); a FastAPI scoring endpoint consuming transactions from PostgreSQL and returning fraud probability; and a README with results, an architecture description, and setup instructions — organized as a repository named `financial-fraud-detection`.

Two decisions shaped everything. First, **methodological honesty over a flattering headline**: the target number (~96.8% recall) would only be reported if a real training run actually produced it at a usable operating point — and when it turned out not to, the README would say so plainly rather than quietly ship a placeholder. Second, **run-out-of-the-box**: because the real dataset is a ~144 MB gated Kaggle download, the repo ships a synthetic generator that mirrors the schema so the whole pipeline executes end-to-end with zero downloads.

The first of those decisions turned out to be the entire story of this project.

## 2. Repository scaffold

The structure follows a conventional ML-project layout so anyone browsing the repo finds things where they expect:

```
financial-fraud-detection/
├── api/            FastAPI serving layer (main, predict, database, schemas, config)
├── data/           dataset lands here (creditcard.csv git-ignored)
├── db/             PostgreSQL schema.sql + bulk CSV loader
├── models/         trained pipeline artifacts (git-ignored, regenerated by training)
├── notebooks/      the EDA notebook
├── reports/figures/ generated charts (git-ignored, regenerated)
├── scripts/        synthetic-data generator + a standalone scoring example
├── src/            all reusable pipeline code (config, preprocessing, models, train, evaluate)
├── tests/          API smoke tests (model + DB stubbed)
├── config.yaml     every hyperparameter and path in one place
├── Dockerfile / docker-compose.yml / requirements.txt / pyproject.toml
```

Why a `config.yaml` at the root: seeds, split ratios, the SMOTE strategy, the full ANN hyperparameter set, the threshold strategy, and every artifact path live in one file (`src/config.py` loads it into an attribute-accessible object), so nothing is hard-coded across modules and retuning never requires touching code. Why `models/` and `data/creditcard.csv` are git-ignored: binary artifacts and a 144 MB licensed dataset don't belong in version control — they're reproducible from code and a download. Two config files, deliberately separate: `src/config.py` (training) and `api/config.py` (serving), so the API image doesn't drag in training-only concerns and the scaler/threshold are loaded as persisted artifacts rather than hard-coded.

## 3. The dataset — acquisition was its own saga

The project uses the **Kaggle "Credit Card Fraud Detection" dataset (mlg-ulb/creditcardfraud)**: 284,807 European card transactions over two days, 492 frauds (0.172%). Features `V1`..`V28` are anonymized PCA components; only `Time` and `Amount` are on their original scale; `Class` is the label.

Getting the file onto the machine took far longer than expected, and every failure was instructive:

- **The classic `kaggle` CLI could not use the account's token.** Kaggle had issued a newer `KGAT_`-style API token, but the installed `kaggle` CLI (1.7.4.5) still expected the legacy `username`+`key` pair and died with `KeyError: 'username'`. It also authenticates *on import*, creating a chicken-and-egg where `kaggle auth login` can't even bootstrap without a credential already present.
- **The network actively fought the download.** Throughout, the machine's firewall reset outbound connections (`ConnectionResetError 10054`), which broke `pip` mid-install and would have broken any browser OAuth callback.
- **The fix was `kagglehub`.** Kaggle's newer Python client reads the `KGAT_` token natively via the `KAGGLE_API_TOKEN` environment variable. `kagglehub.dataset_download("mlg-ulb/creditcardfraud")` pulled the data into its cache in seconds, and a one-liner copied `creditcard.csv` into `data/`. Final file: **150,828,752 bytes** — the correct full dataset.

The lesson worth keeping: when a tool's auth is fighting you, switch tools rather than tokens. `kagglehub` was built for exactly this credential and made the problem disappear.

For anyone without a Kaggle account, `scripts/make_sample_data.py` generates a schema-compatible synthetic CSV (same columns, same ~0.17% fraud rate, with a few PCA-like features shifted for the fraud class so there is learnable signal) purely so the pipeline runs end-to-end. Its metrics are meaningless by construction and the README says so.

## 4. Preprocessing — leakage paranoia

`src/data_preprocessing.py` encodes the one decision that matters most on an imbalanced problem: **SMOTE is fit only on the training fold, never before the split.** The pipeline splits first (stratified 60/20/20 train/val/test), scales second, and resamples third. Oversampling before splitting is the classic leakage bug — synthetic minority samples derived from validation/test rows leak into training and inflate every score. Doing it in this order makes that mistake structurally impossible.

`Amount` and `Time` get a **RobustScaler** (fit on train only) because they carry heavy-tailed outliers that would distort a standard scaler; the 28 PCA components are already standardized and pass through untouched. SMOTE (`sampling_strategy=0.10`) lifted the training fold from its native imbalance to **200,157 rows — 18,196 fraud / 181,961 legit** (~10% fraud, deliberately not 50%, to avoid over-synthesizing the minority). The fitted scaler is persisted with joblib so the API applies exactly the same transform at serving time.

## 5. The models

**The ANN** (`src/models/ann.py`) is a wide-then-narrow fully-connected network, built entirely from `config.yaml` so its shape is a data decision, not a code change. Loss is binary cross-entropy; Adam optimizer; `ReduceLROnPlateau` and `EarlyStopping` both monitor **validation PR-AUC** (`val_auprc`) — the right target on an imbalanced problem, where ROC-AUC and accuracy are far too forgiving. Residual imbalance after SMOTE is handled with class weights.

**The baselines** (`src/models/baselines.py`) — Logistic Regression, Random Forest, XGBoost — are each imbalance-aware (`class_weight="balanced"` / `scale_pos_weight`) and trained on the *identical* SMOTE-resampled fold as the ANN, so the four-way comparison is genuinely fair.

**Threshold optimization** (`src/evaluate.py`) tunes the decision boundary on the validation set rather than leaving it at the naive 0.5 — and the choice of *strategy* here became the crux of the whole project (Section 6).

## 6. The 96.8%-recall reckoning — the heart of this project

The brief asked for "~96.8% recall on the fraud class." The first draft of the README carried that number as a headline. Then the model was actually trained, and the truth was more interesting.

**Run 1 — the honest baseline.** The initial ANN (`[64,32,16]`, dropout 0.30, class weight 5, threshold = max-recall-subject-to-precision≥0.85) produced, on the untouched test set:

| Model | Precision | Recall | F1 | ROC-AUC | PR-AUC |
|---|---|---|---|---|---|
| ANN | 0.820 | 0.837 | 0.828 | 0.978 | 0.720 |
| Logistic Regression | 0.830 | 0.796 | 0.812 | 0.973 | 0.717 |
| Random Forest | 0.854 | 0.837 | 0.845 | 0.969 | 0.868 |
| XGBoost | 0.788 | 0.837 | 0.812 | 0.982 | 0.863 |

Real recall was **83.7%, not 96.8%**. The 96.8% figure had been an aspirational placeholder, and the honest move was to say so out loud rather than ship it. Two things also stood out: the ANN's PR-AUC (0.72) trailed the trees badly (~0.86), and the "96.8% recall" numbers common in fraud tutorials are usually artifacts of **SMOTE-before-split** — a leakage bug this pipeline specifically avoids, which is *why* its honest numbers look lower.

Given the choice of how to proceed, the direction picked was **strengthen the ANN and push recall up honestly** — not fake the number.

**Run 2 — the improvement worked, and the target revealed itself as a mirage.** The ANN was enlarged (`[128,64,32]`, dropout 0.25, L2 1e-4, lr 8e-4, batch 1024, 100 epochs / patience 15, class weight lowered 5→2, ~15k params), and a `target_recall = 0.968` threshold strategy was added. The capacity change did exactly what it should: **PR-AUC jumped 0.72 → 0.853**, now competitive with the trees. But forcing 96.8% recall drove the threshold down to **0.0002**, and the result was pathological for *every* model:

| Model | Precision | Recall | PR-AUC |
|---|---|---|---|
| ANN | 0.002 | 1.000 | 0.853 |
| Random Forest | 0.002 | 1.000 | 0.868 |
| XGBoost | 0.004 | 0.990 | 0.863 |

Recall 100%, precision 0.2% — flag nearly every transaction as fraud. This is not a bug; it's the physics of the problem. A handful of frauds are essentially unrankable, so *demanding* you catch 96.8% of them means predicting almost everything positive. A recall figure is meaningless without the precision it was bought at.

**Run 3 — a defensible operating point.** The threshold strategy was switched to "maximize recall while precision ≥ 0.50" — a real fraud rule (catch as much fraud as possible while keeping at least half your alerts genuine). Tuned threshold 0.0157 (val recall 0.810, val precision 0.500), producing the final, honest, shippable table (Section 7).

The README documents this whole arc, including a standing section — *"A note on inflated recall claims"* — explaining the SMOTE-before-split pitfall. The result: numbers a reader can trust, and a repo that reads as *more* credible than the "99% everything" tutorials, not less.

## 7. Results

Final test-set results (positive class = fraud; ~98 frauds in the 56,961-row hold-out; threshold tuned on validation to max recall at precision ≥ 0.50):

| Model | Precision | Recall | F1 | ROC-AUC | PR-AUC |
|---|---|---|---|---|---|
| **ANN** | 0.394 | 0.867 | 0.541 | 0.966 | **0.853** |
| Logistic Regression | 0.541 | 0.867 | **0.667** | 0.973 | 0.717 |
| Random Forest | 0.451 | **0.898** | 0.601 | 0.969 | **0.868** |
| XGBoost | 0.442 | 0.888 | 0.590 | **0.982** | 0.863 |

Honest reading: the ANN catches **~87% of fraud** and, after the Section-6 rework, its **PR-AUC (0.853) is competitive** with the gradient-boosted trees — a real improvement from 0.72. But the ANN is *competitive, not dominant*: on this tabular PCA data the trees are genuinely hard to beat (Random Forest leads on recall and PR-AUC; Logistic Regression happens to win F1 at this operating point). That is the correct, expected result for a dataset of this shape, and it is reported as-is rather than cherry-picked. The ANN's precision sitting a little under the 0.50 validation floor is expected small-sample threshold transfer — the validation fold has only ~79 frauds.

`src/evaluate.py` concentrates all plotting in one module (headless Agg backend, so training runs on servers without a display) and emits per-model confusion matrices plus overlaid precision-recall and ROC curves.

## 8. Serving — FastAPI + PostgreSQL + Docker

`api/main.py` exposes `GET /health` (model + database status), `POST /score` (inline transaction payload), `GET /score/{id}` (fetch a transaction from PostgreSQL and score it), and `POST /score/batch`. The request schema (`api/schemas.py`) is a Pydantic model mirroring the raw dataset columns with `extra="forbid"`, so malformed input is rejected with a 422 before reaching the model.

`api/predict.py` loads the ANN, the fitted RobustScaler, and the tuned threshold once as a cached singleton, and — critically — applies the *same* scaler to the *same* columns in the same order as training, so serving can never drift from training. TensorFlow is imported lazily inside the predictor so the lighter code paths (and the tests) don't pay for it. `api/database.py` uses SQLAlchemy Core with a pooled engine; `db/schema.sql` defines the `transactions` and `fraud_scores` tables, and `db/load_csv.py` bulk-loads the CSV. `docker-compose.yml` brings up PostgreSQL (schema auto-applied) and the API together; the Dockerfile builds a `python:3.11-slim` image with the scientific stack.

`scripts/predict_example.py` is the fastest way to *see* output without a server or database: it pulls real rows from the CSV, scores them through the saved artifacts, and prints fraud probability + decision next to the true label.

## 9. The EDA notebook

`notebooks/eda.ipynb` tells the analyst's story: integrity checks → class balance (the 1-in-578 imbalance) → `Amount`/`Time` distributions by class → a full correlation heatmap and the features most correlated with `Class` → class-conditional KDEs of the most discriminative PCA components → and a **statistical hypothesis-testing** section. That section runs a **Mann–Whitney U test** per feature (non-parametric, since the PCA components aren't Gaussian) with **Bonferroni correction** across the ~30 simultaneous tests and a **rank-biserial effect size**, so a microscopic p-value on 284K rows isn't mistaken for a large effect. The notebook imports nothing it re-implements — it's the narrative; `src/` is the implementation — and ships with clean, unexecuted cells.

## 10. Verification

The build environment had no heavy dependencies and no network, so verification happened in three honest layers rather than one:

- **Static checks in the build environment.** Every Python module was compiled with `py_compile` (catching syntax errors across all 20+ files) and the notebook JSON was validated. This is all that environment could do — it's stated plainly rather than dressed up as more.
- **Real execution on the user's machine.** The user ran `python -m src.train` on Windows against the real 144 MB dataset. That is where every number in this log and the README comes from — three full runs as the model and threshold strategy evolved (Section 6).
- **Independent CI on clean runners.** GitHub Actions (Section 11) then installed `requirements.txt` from scratch on Ubuntu, ran the pytest suite, ran CodeQL, and built the Docker image — all green. That is the strongest verification of all: the project installs and works on a machine that has never seen it.

The test suite (`tests/test_api.py`) stubs the predictor and database, so it runs fast and needs neither a trained model nor a live PostgreSQL — which is exactly why it passes in CI.

## 11. Publishing to GitHub — the authentication saga

The project went to `github.com/agvs03/financial-fraud-detection` under the user's own identity, but HTTPS auth fought back at every turn, and the sequence is worth recording:

- **`.gitignore` hygiene first.** Before the first commit, the staged set was audited: no `creditcard.csv`, no `.env`, no `kaggle.json`, no model artifacts. A stray `models/threshold.json` slipped in (the ignore rules covered `.keras`/`.joblib` but not `.json`); the pattern was widened and the file un-staged, keeping the initial commit clean.
- **Authorship corrected.** The first commit was made with a placeholder identity; it was amended to the user's real `git config` identity so GitHub attributes it correctly. Later, at the user's request, the `Co-Authored-By` trailer was removed entirely so the commit reads as solely their work — done with `git commit --amend` and verified with `git log`.
- **HTTPS tokens were a dead end.** Password auth is disabled at GitHub; a fine-grained token failed with 403 (it lacked *Contents: write*); an over-scoped classic token was proposed with dangerous permissions (`delete_repo`, `admin:org`) and pared back to `repo` only for least privilege; a push failed because a placeholder `ghp_YOUR_TOKEN` was pasted literally; and pasting into the invisible cmd password prompt (where Ctrl+V does nothing) added more noise. Two live tokens were even pasted into chat and had to be revoked.
- **SSH ended it.** An `ed25519` key was generated, its public half added to GitHub, verified with `ssh -T git@github.com` → `Hi agvs03!`, and the remote switched to `git@github.com:...`. The push went through immediately, and every push since needs no token, no prompt, nothing. The durable lesson: **set up SSH once and the credential problem is gone forever** — worth far more than any token workaround.

## 12. Continuous integration

Three GitHub Actions workflows run on every push to `main`: **Python application** (installs `requirements.txt` on a clean Ubuntu runner and runs the pytest suite + flake8), **CodeQL** (security analysis for Python), and **Docker Image CI** (builds the full TensorFlow image to prove it compiles). All three pass green, and their live status badges — plus Python-version and MIT-license badges — sit at the top of the README.

One CI-shaped issue was pre-empted rather than discovered: the tests import `from api import ...` / `from src import ...`, which a bare CI runner (with no project root on `PYTHONPATH`) would fail to resolve, since pytest doesn't automatically put the rootdir on `sys.path`. A root-level `conftest.py` that inserts the repository root onto `sys.path` was added up front — which is why the very first "Python application" run passed instead of failing on `ModuleNotFoundError`.

## 13. Design principles, in hindsight

Five principles did the most work. **One source of truth**: all hyperparameters in `config.yaml`, all plotting in one module, one shared scaler/feature contract between training and serving. **Leakage paranoia**: SMOTE inside the training fold only, a hold-out set untouched until final evaluation, the threshold tuned on validation rather than test. **Honesty about the numbers**: the 96.8% headline was demoted to the truth (~87% recall) the moment real data contradicted it, the pathological high-recall operating point was diagnosed and rejected, and all four metrics are reported rather than a flattering one. **Least privilege and clean secrets**: the dataset, `.env`, and every credential stay out of the repo; auth ended on SSH. And **verify honestly**: static checks were called static checks, real numbers came from real runs, and CI on a clean machine had the final word — because "it should work" isn't a deliverable.
